# TagsTool

Одноразовый инструмент переноса тегов из `photos.sqlite` в базу сайта.

**Отказ от ответственности.** Это вспомогательная утилита для разовой миграции, а не
часть приложения. Она не покрыта тестами, рассчитана на конкретный формат
`photos.sqlite` и на запуск руками с проверкой результата на каждом шаге.

## Он не трогает проект сервера

Ни ссылки на проект, ни правок в нём.

Для тегов всё, что требует базы или DeepSeek, делается запросами к уже существующему API.
Для векторов такой логики на сервере нет и не будет — команда `embeddings` пишет в
Postgres напрямую, см. раздел [Векторы](#векторы). Это единственное исключение.

Эндпоинты, которые используются для тегов:

| | зачем |
|---|---|
| `POST /v1/Tags/completion` | перевод и алиасы — `GetTagCompletionCommand` |
| `POST /v1/Tags` | создание тега — `AddTagCommand` |
| `GET /v1/Tags` | текущий словарь, чтобы не плодить дубли |
| `PATCH /v1/Media` | простановка тегов — `EditMediaCommand` |

Отсюда следствия: **для тегов строка подключения и ключ DeepSeek не нужны** — их знает
сервер. Нужен только логин и пароль Basic-авторизации, и сервер должен быть запущен на
этапах 2 и 3. Команде `embeddings`, наоборот, нужна строка подключения, но не нужен
запущенный сервер.

Зависимости: `Microsoft.Data.Sqlite` (чтение исходного файла) и `Npgsql` (только для
команды `embeddings`).

## Три этапа

Между этапами — файлы, которые ты правишь руками. В базу пишет только третий.

```bash
# 1. Офлайн, сервер не нужен, ничего не стоит. Гоняй сколько угодно.
dotnet run -- extract --sqlite ../photos.sqlite --out tags.csv

#    >>> правишь tags.csv в Excel <<<

# 2. Каждый keep — один вызов DeepSeek через твой сервер.
#    --threads: сколько тегов переводить одновременно (1..2500, по умолчанию 1)
dotnet run -- translate --in tags.csv --out tags.json --threads 8 \
    --api http://localhost:5101 --user admin --password ...

#    >>> вычитываешь переводы в tags.json <<<

# 3. Создание тегов. Сначала без --assign.
dotnet run -- import --in tags.json \
    --api http://localhost:5101 --user admin --password ...
```

Логин и пароль можно не писать в командной строке:

```powershell
$env:TAGSTOOL_USER = "admin"
$env:TAGSTOOL_PASSWORD = "..."
$env:TAGSTOOL_API = "http://localhost:5101"
```

### Этап 1 на твоих данных

```
Исходных тегов: 1379
После нормализации и склейки форм: 1234
Предзаполнено keep: 436
```

Что склеилось само: регистр (`Japan`/`japan`), подчёркивания и дефисы
(`cherry_blossoms`/`cherry blossoms`), единственное и множественное — но только когда
**обе формы есть в данных**, поэтому `mountain` + `mountains` → 470, а одинокое
`glasses` не калечится.

**Ничего не удаляется.** `--min-count` только предзаполняет колонку `action`: редкий
тег — это то, что делает находимой единственную фотографию вагю-бургера. Колонка
`band` помогает разметить: `core` (≥3 фото), `tail` (2), `single` (1).

Колонки CSV:

| колонка | что делать |
|---|---|
| `slug` | **ключ слияния**: две строки с одинаковым slug станут одним тегом |
| `label` |английская подпись, уйдёт в перевод — правь, если кривая |
| `count` | сколько фотографий |
| `band` | подсказка для разметки |
| `action` | `keep` / `drop` — единственное, что реально решает |
| `duplicate_hint` | кандидаты в дубли, точность ~2/3 — **проверяй** |
| `merged_forms` | что склеилось автоматически |
| `source_tags` | **не удалять**, по нему этап 3 расставляет теги |

Подсказка о дублях считается по векторам: близкие центроиды **и при этом** почти
нулевое совместное появление. Находит `cityscape`/`city`, `water`/`waterfront`,
`table`/`desk`. Но предлагает и `temple`/`shrine`, а их сливать нельзя — 神社 и 寺
разные вещи. Поэтому это подсказка, а не автослияние.

### Этап 2

**Параллельность.** `--threads N`, от 1 до 2500, по умолчанию 1. Каждый поток — это
запрос к твоему серверу, который дёргает DeepSeek, поэтому на больших значениях
упрёшься в рейт-лимит провайдера, а не в инструмент. Разумный диапазон — 4..16;
выше 32 инструмент выводит предупреждение.

Замер на заглушке с задержкой 0.3 с, 40 тегов: `--threads 1` — 13.1 с,
`--threads 16` — 1.8 с.

`--delay` при `--threads > 1` действует на каждый поток отдельно, то есть работает
как простой троттлинг.

**Перезапускаемо.** Сохраняет по ходу дела, при повторном запуске доберёт только
недоделанное. Упавший тег не роняет прогон — записывается с пустым переводом и
подхватится следующим запуском. Порядок в файле всегда по убыванию частоты,
независимо от того, в каком порядке завершились потоки.

**Ctrl+C** перехватывается: инструмент дожидается уже отправленных запросов и
дописывает файл. При параллельной работе в воздухе висит до `--threads` уже
оплаченных ответов, терять их незачем.

Вычитывая `tags.json`, смотри в первую очередь на японский (модель любит катакану там,
где нужен кандзи) и на алиасы (лишние или слишком широкие). Теги без трёх переводов
импорт не пропустит.

### Этап 3

Сначала **без** `--assign` — только словарь. Проверь в админке, что теги появились и
автокомплит работает. Не устроило — удали созданное и вернись на этап 2.

Для `--assign` нужен файл `media-map.json` — карта «имя файла без расширения → id».
Инструмент намеренно не лезет в Postgres, поэтому карту выгружаешь ты:

```sql
SELECT json_object_agg(regexp_replace(file_name, '\.[^.]+$', ''), id)
FROM media_files
WHERE type = 'Image';
```

Сохрани результат как `media-map.json` рядом с инструментом. Дальше:

```bash
dotnet run -- import --in tags.json --sqlite ../photos.sqlite --assign \
    --api http://localhost:5101 --user admin --password ...
```

Файлы с одинаковым набором тегов отправляются одним запросом, так что ~4200 файлов
укладываются в несколько сотен вызовов.

### Откат

Инструмент ничего не удаляет сам. Всё созданное перечислено в `tags.json`:

```sql
DELETE FROM tags WHERE slug IN ('city', 'temple', ...);
-- переводы и связи уйдут каскадом
```

## Важно про результат

Проставленные `--assign` теги — **машинная разметка Qwen, а не твоя**. Она годится
ровно для одного: проверить поиск, фасеты и кликабельные теги на реальном объёме.

Когда начнёшь размечать руками — снеси импортированные связи, иначе через месяц не
отличишь своё от машинного. Словарь при этом можно оставить: 400–600 выверенных тегов
с переводами и алиасами набирать с нуля пришлось бы долго.

# Векторы

Отдельная команда `embeddings`. В отличие от тегов, она **пишет в Postgres напрямую**:
на сервере нет и не будет API для импорта векторов, потому что это ответвление, а не
часть приложения.

Риск от этого небольшой: `media_embeddings` — производная таблица, её содержимое в любой
момент пересобирается из `photos.sqlite` за минуту. Ни одна таблица сервера при импорте не
изменяется, `media_files` только читается.

## Шаг 1. Сущность и миграция (на стороне сервера)

Инструмент пишет в три колонки с конкретными именами. Сущность должна давать ровно их —
при `UseSnakeCaseNamingConvention()` это получается само:

```csharp
public class MediaEmbedding
{
    /// <summary>Одновременно первичный и внешний ключ -> media_file_id</summary>
    public int MediaFileId { get; set; }

    /// <summary>768 float, уже L2-нормализованы -> vector (real[])</summary>
    public required float[] Vector { get; set; }

    /// <summary>id энкодера, напр. google/siglip2-base-patch16-256 -> model</summary>
    public required string Model { get; set; }

    public MediaFile MediaFile { get; set; } = null!;
}
```

```csharp
modelBuilder.Entity<MediaEmbedding>(entity =>
{
    entity.HasKey(e => e.MediaFileId);

    // real[] — обычный массив Postgres, Npgsql маппит его в float[] сам.
    // pgvector НЕ нужен: ранжирование считается в памяти (0.25 мс на 4200 строк).
    entity.Property(e => e.Vector).HasColumnType("real[]");

    entity.HasOne(e => e.MediaFile)
          .WithOne()
          .HasForeignKey<MediaEmbedding>(e => e.MediaFileId)
          .OnDelete(DeleteBehavior.Cascade);
});
```

Отдельная таблица, а не колонка в `MediaFile` — принципиально: вектор весит 3 КБ, и в
`MediaFile` его тянул бы каждый запрос страницы дня.

`DbSet` в `IAppDbContext` добавлять **не обязательно** — инструменту он не нужен, а серверу
пригодится только когда дойдёшь до подсказок по похожести.

Итоговая таблица:

```sql
CREATE TABLE media_embeddings (
    media_file_id integer PRIMARY KEY REFERENCES media_files(id) ON DELETE CASCADE,
    vector        real[] NOT NULL,
    model         text   NOT NULL
);
```

## Шаг 2. Проверка формата, без базы

```bash
dotnet run -- embeddings --sqlite ../photos.sqlite --dry-run
```

```
Векторов в sqlite: 4200
Модель: google/siglip2-base-patch16-256
Объём: 12.3 МБ

--dry-run: к базе не подключались, ничего не записано.
```

Читает файл, сверяет размерность и нормализацию, ничего никуда не пишет. Строка
подключения на этом шаге не нужна.

## Шаг 3. Импорт

```bash
dotnet run -- embeddings --sqlite ../photos.sqlite \
    --connection "Host=localhost;Database=haru;Username=postgres;Password=..."
```

Или через переменную окружения, чтобы пароль не светился в истории команд:

```powershell
$env:TAGSTOOL_CONNECTION = "Host=localhost;Database=haru;Username=postgres;Password=..."
dotnet run -- embeddings --sqlite ../photos.sqlite
```

Ожидаемый вывод:

```
Векторов в sqlite: 4200
Модель: google/siglip2-base-patch16-256
Объём: 12.3 МБ
Изображений в media_files: 4200
Сопоставлено: 4200
Из sqlite без пары в media_files: 0
Изображений в базе без вектора: 0

Готово. В таблице media_embeddings: 4200 строк,
длина вектора от 768 до 768.
```

Две последние строки отчёта — то, на что смотреть. **«Изображений в базе без вектора»**
важнее первой: такие фотографии никогда не появятся в подсказках по похожести, и заметить
это самостоятельно почти невозможно.

## Что команда проверяет и почему падает

- **Размерность и длина блоба.** Ожидается ровно 768 float32 = 3072 байта. Иначе падает,
  а не пишет мусор.
- **Нормализация.** Длина каждого вектора должна быть 1.0 ± 0.01. На этом держится
  равенство «скалярное произведение = косинус»; без него все расчёты похожести
  бессмысленны.
- **Одна модель на всю базу.** Векторы разных энкодеров — разные пространства, сравнивать
  их между собой нельзя. Если в sqlite окажется больше одной модели, импорт остановится.
- **Существование таблицы.** Проверяется до чтения `media_files`, с понятным сообщением
  вместо сырой ошибки Postgres.

## Повторный запуск и откат

Идемпотентно: перед вставкой удаляются только те строки, которые сейчас будут перезаписаны
(`DELETE ... WHERE media_file_id = ANY(...)`), чужие не трогаются. Всё в одной транзакции —
при ошибке посреди импорта не остаётся половины данных.

Откат — обычный SQL, инструмент для этого не нужен:

```sql
DELETE FROM media_embeddings;
```

Флаги `--table` (по умолчанию `media_embeddings`) хватает, если решишь назвать таблицу
иначе.
