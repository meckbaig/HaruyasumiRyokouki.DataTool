# База фотографий (photos.sqlite)

`photos.sqlite` - один файл SQLite с искомыми метаданными фотографий из поездки:
даты, английские описания и теги, японский/английский OCR-текст и мультиязычные
эмбеддинги изображений. Готовится офлайн один раз, приложение из неё
только читает.

Одна строка на фото в таблице `images`; результаты каждой стадии лежат в
отдельных таблицах и связаны по `image_id`.

## Что где лежит

### images (одна строка на фото)

| колонка | смысл |
|---|---|
| `id` | первичный ключ, на него ссылаются остальные таблицы |
| `path` | абсолютный путь к JPEG (UNIQUE) |
| `filename` | имя файла, напр. `PXL_20260115_090000123.jpg` |
| `dup_group` | базовое имя, общее у оригинала и его отредактированных копий (`~2`, ` (2)`); по нему схлопывают почти-дубликаты |
| `taken_at` | время съёмки, строка ISO 8601 (`2026-01-15T09:00:00`) или NULL |
| `taken_source` | откуда взялась дата: `filename`, `exif` или `unknown` |
| `width`, `height`, `orientation` | размеры в пикселях и EXIF-ориентация |
| `status_meta/ocr/vlm/embed` | состояние стадии: `pending`, `done` или `error` |
| `error_meta/ocr/vlm/embed` | текст ошибки стадии, если она упала (по каждой стадии отдельно) |

### ocr (текст, Apple Vision, японский + английский)

| колонка | смысл |
|---|---|
| `image_id` | -> images.id |
| `text` | все распознанные строки через перевод строки (может быть пустым - это норма) |
| `blocks_json` | JSON-массив `{text, confidence, bbox}`; `bbox` это `[x, y, w, h]`, нормализовано 0..1, начало внизу-слева (конвенция Apple Vision); `confidence` 0..1 |
| `lang_hint` | грубая оценка: `ja`, `en`, `mixed` или NULL |

### vlm (описание, теги, сцена от Qwen2.5-VL)

| колонка | смысл |
|---|---|
| `image_id` | -> images.id |
| `description` | английский, 1-3 фактических предложения |
| `tags_json` | JSON-массив тегов в нижнем регистре (объекты, сцена, активности) |
| `scene_setting` | `indoor`, `outdoor` или NULL |
| `scene_category` | короткая свободная метка, напр. `temple`, `street`, `food` |
| `time_of_day` | `day`, `night`, `dusk` или NULL |
| `location_guess` | JSON `{name, confidence, reasoning}` - догадка, `name` = NULL когда модель не уверена; не считать за истину |
| `raw_json` | полный JSON модели, чтобы поля можно было пересобрать без повторного прогона |

### embeddings (векторы изображений, SigLIP 2, мультиязычные)

| колонка | смысл |
|---|---|
| `image_id` | -> images.id |
| `model` | id энкодера, напр. `google/siglip2-base-patch16-256` |
| `dim` | длина вектора (768) |
| `vector` | BLOB: `dim` штук float32, уже L2-нормализованы |

## Как использовать

### Семантический поиск по эмбеддингам (основное)

Это главный механизм: поиск по смыслу, а не по словам. Он находит нужное по
синонимам («noodle soup» находит фото с тегом `ramen`) и по запросу на любом из
трёх языков (японский, английский, русский) - переводить запрос не нужно.

Как искать:

1. Закодировать текст запроса **тем же** текстовым энкодером SigLIP 2 и
   L2-нормализовать результат (см. ниже про кодирование вне Python).
2. Так как векторы нормализованы, косинусная близость = скалярное произведение.
   Посчитать его между вектором запроса и `vector` каждой строки.
3. Отсортировать по убыванию, взять top-k.
4. Отсекать по порогу около `0.10`: релевантные совпадения дают ~0.12-0.19; если
   в наборе ничего подходящего нет, верхний score падает до ~0.08 и выдача
   становится «притянутой». Порог позволяет показать «ничего не нашлось» вместо
   мусора.

4200 векторов это ~12 МБ; полный перебор ранжирует за единицы миллисекунд, так
что векторный индекс не нужен. Алгоритм ранжирования в псевдокоде:

```
# вектор запроса q и вектор фото v оба L2-нормализованы
score(q, v) = sum(q[i] * v[i])      # скалярное произведение = косинус
# посчитать score для каждой строки embeddings, отсортировать по убыванию,
# отбросить всё ниже порога, взять top-k
```

**Кодирование запроса.** Сами векторы фото уже посчитаны и лежат в базе; на
каждый запрос нужно закодировать только его текст - тем же текстовым энкодером
SigLIP 2 (id модели лежит в колонке `embeddings.model`), затем L2-нормализовать.
Само ранжирование (скалярное произведение по сохранённым векторам и сортировку)
приложение считает у себя. Два обычных способа получить вектор запроса:

- поднять небольшой сервис, который кодирует текст энкодером SigLIP 2 и
  возвращает 768 чисел;
- либо экспортировать текстовый энкодер SigLIP 2 в ONNX и гонять его в процессе
  (напр. через ONNX Runtime).

### Полнотекст по OCR и тегам (для точного текста)

Семантика не «читает» текст на фото. Чтобы найти «фото, где на вывеске написано
`マルイ`» или код станции вроде `JR`, нужен точный текст. Искать по `ocr.text` и
`vlm.tags_json` (описание для этого не берём - оно многословное и переполняет
выдачу). Для сайта лучше построить индекс FTS5, а не `LIKE`:

```sql
CREATE VIRTUAL TABLE search_fts USING fts5(image_id UNINDEXED, ocr, tags);
INSERT INTO search_fts
  SELECT o.image_id, o.text, v.tags_json
  FROM ocr o JOIN vlm v ON v.image_id = o.image_id;

SELECT image_id FROM search_fts WHERE search_fts MATCH 'ラーメン';
```

### Комбинирование

Использовать оба слоя вместе: семантику как основной поиск «по смыслу / на любом
языке» с порогом, и FTS по OCR+тегам для точных надписей, брендов, названий
станций. При ранжировании имеет смысл бустить то, что попало и в семантику, и в
полнотекст.

### Фильтры (обычный SQL)

```sql
SELECT id FROM images WHERE taken_at >= '2026-01-15' AND taken_at < '2026-01-20';

SELECT MIN(id) FROM images GROUP BY dup_group;

SELECT id FROM vlm WHERE scene_category = 'temple';
```

## Нюансы

- `location_guess.name` - догадка и часто NULL. Только подсказка, не подтверждённое
  место.
- `description` богатое, но многословное; для поиска по словам и фасетов лучше
  `tags_json`, а `description` - для показа.
- `path` абсолютный и указывает туда, где фото лежали при обработке; при переносе
  фото пути надо перепривязать.
- Пустой `ocr.text` для фото без текста - нормальный результат, не ошибка.
